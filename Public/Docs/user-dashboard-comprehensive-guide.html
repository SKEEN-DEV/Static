1. Dashboard Overview

The User Dashboard is a comprehensive, real-time monitoring interface that provides users with instant visibility into their key tasks, content, and data across the MCD platform. Built with React/TypeScript, it features automatic polling, new item detection, and responsive widget-based architecture.

Key Capabilities
  • Real-time Updates: Automatic polling every 60 seconds keeps data fresh
  • New Item Tracking: Visual highlighting of new items with 2-hour timeout
  • Responsive Design: Widgets adapt to different screen sizes
  • Quick Actions: Fast access to create contacts, outlets, interactions, subjects, and distributions
  • Unified Search: Powerful search overlay with mode toggle (Your Work / Media)
  • Permission-Based: Widgets and actions respect user permissions via demo mode configuration
✅ Organizational Improvements (May 2026)

The dashboard codebase has been refactored with domain-driven architecture improvements:

  • Priority 1: Common UI components centralized in Components/Common/UI/
  • Priority 2: Hooks organized by domain into Hooks/Config/ and Hooks/Data/
  • Priority 3: Settings consolidated in Components/Settings/
  • Priority 4: Promo components extracted to Components/Promos/
  • Priority 5: Types organized into Types/Config/ and Types/Core/

See Section 9: Technical Architecture for complete folder structure and how everything fits together.

2. Client Preset Selector & Permission System

2.1 Overview

The Client Preset Selector is a powerful feature located in the dashboard header that allows developers and admins to control which dashboard widgets and features are visible based on simulated or real user permissions. This is essential for testing different client configurations and preparing for production deployment.

📍 Location

Component: Components/ClientPresetSelector/ClientPresetSelector.tsx

Position: Dashboard header, next to the greeting message

Visibility: Shown to SysAdmin users only (controlled by AuthToken.HasSysAdminRole())

Why Client Presets Exist

Different Vuelio clients have vastly different subscriptions and feature access. Some are SRM-focused (interactions, subjects, contacts), others are media-focused (monitoring, distributions, journalist enquiries), and enterprise clients have everything. The preset selector lets you:

  • ✅ Test the dashboard as different client types without multiple accounts
  • ✅ Verify permission logic works correctly before production release
  • ✅ Demo specific feature sets to potential clients
  • ✅ Switch between real auth-based permissions and custom configurations
  • ✅ Ensure locked widget promos display correctly when features are unavailable

2.3 Permission Mappings

Each dashboard module (widget group) maps to specific AccessArea permission flags from the authentication system. The system supports both legacy Vuelio permissions and modern MCD permissions for backward compatibility.

Complete Permission Mapping Table

Dashboard Module Widgets Controlled AccessArea Permission(s) Helper Function Value(s)
interactions My Interactions, Incoming Interactions, Interactions Leaderboard, and interaction charts Interaction OR MCDInteraction HasAccessToInteractionsOrIsSysadmin() 4 or 8388608
subjects Subjects widget Subject HasAccessToSubjectsOrIsSysadmin() 4194304
groups Groups widget Database OR MCDDatabase HasAccessArea() (manual check) 1 or 8192
jesEnquiries JES Enquiries widget Jes HasAccessArea(AccessArea.Jes) 32
politicalGroups Political Groups widget MCDPoliticalDatabase OR PoliticalDatabase HasAccessArea() (manual check) 67108864 or 512
distributions Distributions widget Release OR MCDRelease HasAccessToReleasesOrIsSysadmin() 2 or 1048576
forwardFeatures Forward Features widget Release OR MCDRelease HasAccessToReleasesOrIsSysadmin() 2 or 1048576
featureGroups Feature Groups widget MCDPoliticalMonitoring HasAccessArea(AccessArea.MCDPoliticalMonitoring) 16777216
latestMonitoring Latest Monitoring widget MediaMonitoring HasAccessToMediaMonitoringOrIsSysadmin() 131072
⚠️ Bitwise Flag System

AccessArea values use bitwise flags (powers of 2: 1, 2, 4, 8, 16, 32...) for efficient storage. Multiple permissions can be combined in a single number using OR operations. Example: A user with Database (1) + Interaction (4) + Jes (32) = 37.

The subscribedDataAreas field in the auth token stores an array of these numbers as a JSON string: "[4, 16, 32, 4194304]"

2.4 Legacy vs Modern Permissions

Vuelio's permission system evolved from the original platform to the modern MCD system. To support both legacy and new clients, the dashboard checks hybrid permissions - accepting either the old or new equivalent.

Permission Evolution Table

Feature Legacy Permission Modern Permission Strategy
Interactions Interaction = 4 MCDInteraction = 8388608 ✅ Hybrid - Check both
Releases/Distributions Release = 2 MCDRelease = 1048576 ✅ Hybrid - Check both
Database/Groups Database = 1 MCDDatabase = 8192 ✅ Hybrid - Check both
Political Database PoliticalDatabase = 512 MCDPoliticalDatabase = 67108864 ✅ Hybrid - Check both
Subjects No legacy equivalent Subject = 4194304 🆕 Modern only
Political Monitoring No legacy equivalent MCDPoliticalMonitoring = 16777216 🆕 Modern only
Media Monitoring No legacy equivalent MediaMonitoring = 131072 🆕 Modern only
JES Enquiries Jes = 32 (same for both) 🔄 Shared
✅ Why This Matters

By supporting both legacy and modern permissions, the dashboard works correctly for:

  • 📜 Legacy Vuelio clients migrated from the old platform
  • 🆕 New MCD clients onboarded to the modern system
  • 🔄 Clients mid-migration transitioning between systems

Helper functions like HasAccessToReleasesOrIsSysadmin() automatically check BOTH the legacy and modern flags, so you don't have to manually check each one.

Permission Checking (permissions.ts)

import AuthToken, { AccessArea } from '@components/Common/Permission/AuthTokenHelper';

export const getRealUserPermissions = (auth: IAuthModel): DashboardDemoModules => {
    if (!auth?.data?.authenticated) {
        return { /* all false */ };
    }

    return {
        // Hybrid check - accepts legacy OR modern
        interactions: AuthToken.HasAccessToInteractionsOrIsSysadmin(),
        
        // Modern only
        subjects: AuthToken.HasAccessToSubjectsOrIsSysadmin(),
        
        // Hybrid check
        groups: AuthToken.HasAccessArea(AccessArea.Database) || 
                AuthToken.HasAccessArea(AccessArea.MCDDatabase),
        
        // Shared (same for legacy and modern)
        jesEnquiries: AuthToken.HasAccessArea(AccessArea.Jes),
        
        // Hybrid check
        politicalGroups: AuthToken.HasAccessArea(AccessArea.MCDPoliticalDatabase) ||
                        AuthToken.HasAccessArea(AccessArea.PoliticalDatabase),
        
        // Hybrid check
        distributions: AuthToken.HasAccessToReleasesOrIsSysadmin(),
        forwardFeatures: AuthToken.HasAccessToReleasesOrIsSysadmin(),
        
        // Modern only
        featureGroups: AuthToken.HasAccessArea(AccessArea.MCDPoliticalMonitoring),
        latestMonitoring: AuthToken.HasAccessToMediaMonitoringOrIsSysadmin(),
        
        showFeatureBanner: true
    };
};

3. Polling & Refresh Mechanism

What is Polling?

Polling is a technique where the application automatically checks for new data at regular intervals. Instead of manually clicking a refresh button every time you want to see if there's new content, the dashboard automatically fetches the latest data in the background.

How Polling Works in the Dashboard
  1. Initial Load: When you first open the dashboard, all widgets fetch their data immediately
  2. Background Polling: Every 60 seconds, each widget automatically fetches fresh data from the API
  3. Smart Detection: The system compares new data with previous data to identify newly added items
  4. Visual Feedback: New items are highlighted with a blue left border and subtle background tint
  5. Count Badge: The refresh button shows a numbered badge indicating how many new items have been detected

Refresh Behavior

Automatic (Background) Refresh

  • Interval: 60 seconds (configurable per widget)
  • Behavior: Silently fetches data in the background without showing loading states
  • New Item Detection: Active - compares with previous data and highlights new items
  • Pause Condition: Automatically pauses when browser tab is inactive (saves resources)
  • Resume Condition: Immediately fetches fresh data when tab becomes active again

Manual Refresh (User-Initiated)

  • Trigger: User clicks the refresh button on a widget
  • Behavior: Shows loading state while fetching
  • New Item Detection: Inactive - clears new item highlights and count badge
  • Use Case: User acknowledges they've seen the new items

Implementation Example

// Hook configuration
const { 
    interactions, 
    isLoading, 
    newItemsCount, 
    newItemIds, 
    refresh 
} = useInteractionsData({
    enablePolling: true,        // Enable automatic polling
    pollingInterval: 60000      // Poll every 60 seconds (60,000ms)
});

// Manual refresh clears new items
const handleRefresh = async () => {
    clearNewItems();  // Remove highlights and badge
    await refresh();  // Fetch fresh data
};
Page Visibility Optimization

All widgets use the Page Visibility API to detect when the browser tab is inactive. When you switch to another tab, polling automatically pauses to save server resources and browser performance. When you return to the dashboard tab, it immediately fetches fresh data to ensure you see the latest information.

4. New Item Tracking System

Overview

The dashboard implements a sophisticated new item tracking system that visually highlights recently added content. This helps users quickly identify what's new since they last checked the dashboard.

How It Works

🔍 Detection

On each background refresh (polling), the system compares newly fetched item IDs against previously seen IDs stored in a ref.

✨ Highlighting

New items receive a 3px blue left border, subtle background tint (4% opacity), and a smooth fade-in animation (0.4s).

🔢 Count Badge

The refresh button displays a numbered badge showing the total count of new items detected.

⏱️ Auto-Clear

After 2 hours, new item highlights automatically fade away. They also clear on manual refresh or page reload.

Visual Styling

Element Style Purpose
Left Border 3px solid #3597FE (picton blue) Primary indicator that item is new
Background Tint rgba(52, 152, 219, 0.04) Subtle background highlight (4% opacity)
Animation fadeInSlide (0.4s ease-out) Smooth appearance from left with opacity fade
Count Badge Blue circle with white text Shows total new items count on refresh button

Timeout Behavior

New items are tracked for 2 hours (7,200,000 milliseconds). This ensures:

  • Users have adequate time to review new content
  • The dashboard doesn't accumulate highlights indefinitely
  • Fresh highlights remain meaningful and actionable

Clear Conditions

New item highlights and count badges are cleared when:

  1. Manual Refresh: User clicks the refresh button
  2. Page Reload: User refreshes the entire page
  3. 2-Hour Timeout: Automatic timeout expires

Implementation Pattern

// In custom hook (e.g., useInteractionsData.ts)
const [newItemIds, setNewItemIds] = useState<Set<number>>(new Set());
const previousIdsRef = useRef<Set<number>>(new Set());
const newItemsTimeoutRef = useRef<NodeJS.Timeout | null>(null);
const TWO_HOURS_MS = 2 * 60 * 60 * 1000;

// On background refresh
if (isBackgroundRefresh && !isInitialLoadRef.current) {
    const addedItems = newData.filter(item => 
        !previousIdsRef.current.has(item.id)
    );
    
    if (addedItems.length > 0) {
        const addedIds = new Set(addedItems.map(i => i.id));
        setNewItemIds(prev => new Set([...Array.from(prev), ...Array.from(addedIds)]));
        
        // Set 2-hour timeout
        newItemsTimeoutRef.current = setTimeout(() => {
            setNewItemsCount(0);
            setNewItemIds(new Set());
        }, TWO_HOURS_MS);
    }
}

// In component (e.g., InteractionsContent.tsx)
const isNewItem = newItemIds.has(interaction.id);
return <DashboardListItem isNew={isNewItem} .../>;

const performSearch = async () => {
    setLoading(true);
    try {
        const promises: Promise<SearchResult[]>[] = [];

        if (searchMode === 'work') {
            // Check permissions before adding to search queue
            const canAccessInteractions = !demoModules || demoModules.interactions;
            const canAccessSubjects = !demoModules || demoModules.subjects;
            const canAccessGroups = !demoModules || demoModules.groups;
            const canAccessDistributions = !demoModules || demoModules.distributions;

            if (canAccessInteractions) promises.push(searchInteractions());
            if (canAccessSubjects) promises.push(searchSubjects());
            if (canAccessGroups) promises.push(searchGroups());
            if (canAccessDistributions) promises.push(searchDistributions());
        }

        // Wait for all searches to complete (blocking)
        const results = await Promise.all(promises);
        
        // Flatten and sort by modified date (most recent first)
        const combined: SearchResult[] = results
            .flat()
            .sort((a, b) => new Date(b.modified).getTime() - new Date(a.modified).getTime());

        setResults(combined);
    } catch (error) {
        console.error('Search failed:', error);
        setResults([]);
    } finally {
        setLoading(false);
    }
};

6.3 Search Algorithm & Result Mixing

Parallel Search Execution

All entity type searches execute simultaneously in parallel using Promise.all(). This maximizes performance by not waiting for each search to complete sequentially.

How Promise.all() Works
  • Starts all searches simultaneously: All API calls fire at t=0ms
  • Waits for slowest to complete: Blocks until ALL searches finish
  • Returns combined results: Only updates UI once with complete dataset
  • Fails fast: If any search throws an error, the whole operation fails (unless caught individually)

Result Mixing Algorithm

Once all searches complete, results are combined and sorted using this algorithm:

// Step 1: Wait for all searches to complete (blocking)
const results = await Promise.all(promises);
// At this point: results = [
//   [interaction1, interaction2, ...],  // 10 interactions
//   [subject1, subject2, ...],          // 10 subjects
//   [group1, group2, ...],              // 10 groups
//   [distribution1, distribution2, ...] // 10 distributions
// ]

// Step 2: Flatten nested arrays into single array
const flatResults = results.flat();
// Now: flatResults = [interaction1, interaction2, ..., subject1, subject2, ..., group1, ...]
// Total: up to 40 results (Work mode) or 30 results (Media mode)

// Step 3: Sort by modified date (most recent first)
const combined = flatResults.sort((a, b) => 
    new Date(b.modified).getTime() - new Date(a.modified).getTime()
);
// Now: combined = [mostRecentItem, secondMostRecent, thirdMostRecent, ...]
// Results are INTERLEAVED by recency, not grouped by type

// Step 4: Update state to display results
setResults(combined);

Field Matching & Highlighting

The search includes intelligent field matching to show users where the search term was found:

const detectMatchedField = (data: any, searchTerm: string) => {
    const fieldsToCheck = [
        { key: 'name', label: 'Name' },
        { key: 'headline', label: 'Headline' },
        { key: 'description', label: 'Description' },
        { key: 'interactionTypeName', label: 'Type' },
        { key: 'statusName', label: 'Status' },
        { key: 'tagNames', label: 'Tags' },
        { key: 'ownerName', label: 'Owner' },
        // ... more fields
    ];

    for (const field of fieldsToCheck) {
        const value = data[field.key];
        if (Array.isArray(value)) {
            // Handle array fields (tags, business units, etc.)
            const matches = value.filter(v => 
                containsSearchTerm(String(v), searchTerm)
            );
            if (matches.length > 0) {
                return { field: field.label, value: matches.join(', ') };
            }
        } else if (containsSearchTerm(String(value), searchTerm)) {
            return { field: field.label, value: String(value) };
        }
    }
    return null; // No match detected in checked fields
};

// Display matched field in UI
if (result.matchedField && result.matchedValue) {
    return (
        <div className="result-snippet">
            <strong>Match in {result.matchedField}:</strong>
            {highlightText(result.matchedValue, searchTerm)}
        </div>
    );
}

Highlighting Implementation

const highlightText = (text: string, searchTerm: string): React.ReactNode => {
    if (!searchTerm || !containsSearchTerm(text, searchTerm)) {
        return text;
    }

    // Split text by search term (case-insensitive)
    const regex = new RegExp(`(${searchTerm})`, 'gi');
    const parts = text.split(regex);

    // Wrap matching parts in <mark> tags
    return parts.map((part, index) => 
        regex.test(part) ? (
            <mark key={index} className="highlight">{part}</mark>
        ) : (
            part
        )
    );
};

Performance Considerations

  • Debouncing (500ms): Prevents excessive API calls while typing
  • Minimum 2 characters: Avoids searching on single-letter input
  • Result limits (10 per type): Keeps API response sizes manageable
  • Parallel execution: Maximizes speed by searching simultaneously
  • Graceful failure: Individual search failures return empty arrays, don't crash entire search
  • Client-side sorting: Fast in-memory sort after API calls complete

User Experience Flow

  1. User opens search overlay (Cmd/Ctrl + K or click search button)
  2. Search input auto-focuses
  3. User types search term (e.g., "marketing")
  4. 500ms debounce timer starts
  5. User continues typing → debounce resets
  6. User stops typing → debounce completes after 500ms
  7. Loading spinner appears
  8. All searches fire simultaneously in parallel
  9. System waits for slowest API to complete (typically 500-1000ms)
  10. Results are flattened, sorted by recency, and displayed
  11. User sees up to 40 results (Work mode) or 30 results (Media mode)
  12. Search terms are highlighted in yellow within results
  13. Matched fields shown as snippets ("Match in: Description")
  14. User can filter by entity type using quick filter buttons
  15. Clicking interactions, subjects, distributions, monitoring, JES enquiries, and forward features opens a detail modal
  16. Supported modals provide a "View Full" path for full-page navigation where implemented
  17. Other entity types (for example groups, contacts, outlets) navigate directly via links

// Tab filtering logic
const filterByTab = (tab: InteractionTabId, interactions: Interaction[]) => {
    const now = moment();
    const twoDaysFromNow = moment().add(2, 'days');
    
    switch (tab) {
        case 'overdue':
            return interactions.filter(i => 
                i.deadlineDateTime && 
                moment(i.deadlineDateTime).isBefore(now) &&
                i.statusName !== 'Complete'
            );
        case 'dueSoon':
            return interactions.filter(i => 
                i.deadlineDateTime &&
                moment(i.deadlineDateTime).isBetween(now, twoDaysFromNow) &&
                i.statusName !== 'Complete'
            );
        case 'scheduled':
            return interactions.filter(i => 
                (!i.deadlineDateTime || moment(i.deadlineDateTime).isAfter(twoDaysFromNow)) &&
                i.statusName !== 'Complete'
            );
        case 'completed':
            return interactions.filter(i => i.statusName === 'Complete');
    }
};

            title={currentBanner.title}
            description={currentBanner.description}
            ctaText={currentBanner.ctaText}
            onCtaClick={handleCustomizeClick}
            onDismiss={() => {
                dismissBanner(currentBanner.id);
                setDemoModules({ ...demoModules, showFeatureBanner: false });
            }}
        />
    ) : null;
})()}

Best Practices

  • Unique IDs: Use descriptive, versioned IDs (e.g., feature-name-v1)
  • Change ID to Reactivate: When updating content, increment version (v1 → v2)
  • Keep it Concise: Banner descriptions should be 1-2 sentences max
  • Clear CTA: Action button text should describe the next step
  • Visibility Logic: Hide banners in search mode, settings view, or other focused contexts

Architecture Principles

1. Domain-Driven Organization

The codebase is organized by domain and responsibility rather than by file type:

  • Components/Widgets/ - All widget implementations in one place
  • Components/Common/UI/ - Reusable UI components used across widgets
  • Components/Promos/ - All promotional and subscription modals
  • Components/Settings/ - Settings tab content components
  • Hooks/Config/ - Configuration management hooks
  • Hooks/Data/ - Data fetching hooks with polling
  • Types/Config/ - Configuration type definitions
  • Types/Core/ - Core type definitions

2. Barrel Exports

Each major folder includes an index.ts barrel export for clean imports:

// Instead of:
import { DashboardCard } from '../Common/UI/DashboardCard/DashboardCard';
import { ToggleGroup } from '../Common/UI/ToggleGroup/ToggleGroup';

// Use barrel export:
import { DashboardCard, ToggleGroup } from '../Common/UI';

3. Hook Reusability

All data hooks follow the same pattern and can be used anywhere:

// From any component
import { useInteractionsData } from '../../Hooks';

const { data, isLoading, newItemIds, refresh } = useInteractionsData({
    enablePolling: true,
    pollingInterval: 60000
});

4. Component Composition

Widgets compose smaller, reusable components:

<DashboardCard
    title="Interactions Leaderboard"
    icon={<Icon symbol="Premium" />}
    loading={isLoading}
    configContent={renderConfigContent()}
    size={currentSize}
    onSizeChange={onSizeChange}

>
    <LuminaBarChart 
        data={chartData}
        orientation="horizontal"
        animated={true}
        showValues={true}
    />
</DashboardCard>

How It All Fits Together

Component Flow
  1. UserDashboard.tsx loads widget configuration from useDashboardConfig()
  2. For each visible widget, it renders the corresponding component from Components/Widgets/
  3. Each widget uses a data hook from Hooks/Data/ to fetch its data
  4. Data hooks automatically poll every 60 seconds using the Page Visibility API
  5. Widgets render using shared UI components from Components/Common/UI/
  6. New items are highlighted using CSS classes and tracked via React state
  7. Widget config (size, time range) is managed via DashboardCard config dropdown
  8. All types are imported from Types/Config/ or Types/Core/

State Management

  • Local Component State: UI-specific state (active tab, visible count, modals)

10. Future Improvements

High Priority

JES Enquiries - Relative Date Ranges

Issue Identified: April 2026

Problem: Saved searches store absolute dates that become outdated. Example: A search saved on March 3 for "March 3 - April 2" returns 0 results when run in late April.

Solution: Store relative date periods ("Last 7 days", "Next 7 days", "Next month") and calculate actual dates at runtime from current date. This keeps saved searches and dashboard widgets always current.

Documentation: See /apps/mcd/src/Containers2/JesEnquirySearch/README.md "Future Improvements" section for implementation details.

Server-Side Filtering for Tabs

Currently, tabs in Interactions and other widgets use client-side filtering after fetching all data. This means pagination is inaccurate (showing "20 of 45" when there might be 100 total on the server).

Recommendation: Pass tab filter criteria to API queries so pagination counts reflect actual server totals.

Performance Optimization

  • Reduce polling frequency: Implement exponential backoff (30s → 60s → 120s) when no changes detected
  • Batch API calls: Quick Stats makes 4 separate API calls - consider backend aggregation endpoint
  • Virtual scrolling: For widgets with 100+ items, implement windowing to reduce DOM nodes
